## MotoCam v0.1.18

Release date: 2026-11-19 (tag `v0.1.18`). Pre-release with a debug APK, like v0.1.17. From this release `pubspec.yaml` follows the tag: `0.1.18+18` (Android versionName 0.1.18, versionCode 18).

### Upgrade notes / breaking changes

- **iOS is no longer part of the project.** MotoCam is Android only; the `ios/` folder, the iOS CI job and the iOS release checks are gone. Nothing changes for Android riders.
- Installing over v0.1.13 or earlier: read the upgrade notes of v0.1.14 first (rides move to private storage and are no longer reachable over USB).
- The APK is debug-signed, like v0.1.17. It installs over v0.1.17 (same key and a higher versionCode). If Android refuses it over another MotoCam build, do not uninstall without saving your rides first: uninstalling deletes the rides in MotoCam's private storage.

### Highlights

- **Less work on the app's main thread while recording.**
  - Slow sensor streams (the orientation sensors used by crash detection) are now averaged on a background thread, so the main thread gets about 15 of their messages a second instead of about 101. The sensors_plus plugin is vendored at 7.1.1 for this (`third_party/sensors_plus`, patch notes in `MOTOCAM_PATCHES.md`). The accelerometer that crash detection's jolt check uses still delivers every sample.
  - The accelerometer no longer makes the screen rebuild on every sample.
  - The 15 s device poll rebuilds only the Battery and Temp items instead of the whole status area.
- **Android only.** iOS code paths, CI and docs are removed.

### Checked on a phone (one vivo phone, Android 13, bench, AC power)

These checks ran on a debug build of commit `1ed4566` (the main-thread changes) plus debug-only diagnostics. The tagged commit adds only the iOS removal and this release's version and notes on top of `1ed4566`; that part passed `flutter analyze` and `flutter test` and was not run on a phone.

- 2160p 60 fps, Perfetto trace (2026-11-19): the main thread received about 15 orientation-sensor messages a second (before: about 101), and about 2.5 widget rebuilds a second (before: about 10); the 15 s device poll's frame took 44 ms; crash detection still saw a tip-over input. The total main-thread CPU time did not go down measurably.
- 1080p 30 fps (2026-11-19):
  - A segment roll with the phone locked and the screen off lost 0.29 s of video; an unlocked roll lost 0.19 s; the ride's timeline matched the files within 0.23 s. The 6.6 s loss listed as a known issue in v0.1.17 (measured at 2160p 60 fps on an older build) did not reproduce.
  - The clips held 29.9 frames a second.
  - Import of v0.1.12-format rides (badges, Delete originals, second import) and Save to gallery, Remove copies and deleting a ride with copies all worked.

### Known issues

- **2160p 60 fps clips hold about 42 to 45 frames a second** (unchanged; see v0.1.17). 1080p 30 fps holds its frame rate.
- **Crash detection (jolt + confirm) has not been tested on a real ride.**
- In the Save to gallery dialog, the "already in the gallery" count can include a copy that was deleted outside MotoCam; the save itself copies it again.
- Not checked on a phone: the storage budget, Android 9, 10 and 14 or later, a release-signed build.

### Validation

- `flutter analyze` and `flutter test` passed, and `pwsh ./scripts/release-security-precheck.ps1` passed (results in the GitHub release).
- The phone checks above.
