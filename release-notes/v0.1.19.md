### Highlights

- **Ride export (roadmap T0-1).** The ride's actions menu in Ride History, and a new menu in the playback app bar, now offer **Export to folder** and **Share** (Android).
  - One dialog chooses the clips (locked and incident clips, or all clips, with counts and sizes) and whether to include the ride data (route, speed every second and private file paths; needed to check the signature). Leaving the ride data out hands over video only, with no key material in the export.
  - **Export to folder** copies into a folder the rider picks, in a subfolder named for the ride and the choice, so running the same choice again continues it. Every copy is read back and hashed; a file already there and equal is skipped; a different file of the same name (same size with other content, or longer) is never overwritten; a shorter one is a partial copy from a killed run and is replaced. The clips come first, then the ride JSON (byte for byte, so its checksum and signature stay valid), then `manifest.json` and `MOTOCAM-EXPORT.txt`. A folder without `MOTOCAM-EXPORT.txt` is an incomplete export.
  - **Share** opens the Android share sheet with the same files through a read-only FileProvider.
  - Each clip is also compared with the hash recorded when the ride was saved. A clip that differs, or has none, is still exported and is labelled in the manifest and the README.
  - `MOTOCAM-EXPORT.txt` says in plain words what the export is, what its integrity line means (signed, unsigned checksums, older format, failed or no integrity data), which clips are not included and why, how to check the clip hashes, the payload hash and the signature (with an `openssl` recipe), and what to keep private. `manifest.json` (format 1) holds the same facts for programs. Neither file is signed. The format is documented in `docs/data-formats.md`.
  - One export runs at a time. It is refused while a recording starts, runs or stops, while the migration, import or storage budget runs, and while the ride file is being saved. A recording that starts pauses it; it can be run again to continue. A ring on the ride (or a spinner in playback) shows progress and stops the export when tapped. The screen stays on while it runs.
  - **A section of the ride.** The dialog has a third clips choice, **A section of the ride** (any ride with a timeline, one-clip rides included): exact seconds, video only. A two-handle slider in whole seconds over the ride, with clip-start ticks and lock and incident marks, and `-1 s` and `+1 s` buttons for each end, shows a live label such as `05:12 to 06:40 (1 min 28 s), 2 files, about 310 MB`. It starts on the first minute from Ride History, and from playback on 30 s before to 30 s after the playhead. Clips inside the range are copied unchanged; a clip cut by either end is trimmed without re-encoding and keeps its original file name. A section carries no ride data and no signature, and the dialog says so. The folder is named `MotoCam ride <id> (section 05m12s to 06m40s)`, the manifest says `clips: "section"` with a `section` object (`fromMs`, `toMs`, `actualFromMs`) and, per file, `trimmed`, `clipFromMs` and `clipToMs`, and the README gives the section in ride time and clock time and, per file, `(trimmed)` or `(whole clip)` with its range inside the clip. Running the same section again replaces the trimmed copies.
- **Diagnostic log.** App errors are now kept on the phone in a diagnostic log (`<filesDir>/diagnostics/app.log`, rotated at about 1 MB, two files kept), so a tester can send what went wrong: errors the app caught, framework and uncaught errors with their stack traces, uncaught Android exceptions (written before the app closes), a header at each start (app version, build, phone model, Android version) and, on Android 11 and later, why the app's process ended before (crash, native crash, freeze (ANR) with part of its trace, low memory and so on). It never holds a position, speed or route, and web addresses are cut to their host. The recording settings sheet's About area has **Share diagnostic log** (with a confirm saying what the log holds and that it has no location) and **Clear diagnostic log**. Console output is unchanged.
- **Documentation.** `docs/data-formats.md` (the export folder, the manifest, the README and the checking steps), `docs/platform-integration.md` (the `ride_export` channel, request code 7103 and the FileProvider), `docs/features.md`, `docs/playback-and-history.md` and `docs/development.md` describe ride export.

### Known limits

- No resume journal and no saved folder grant: to continue a stopped export, run it again and pick the same folder; files already there are skipped, and each skip reads both copies again to hash them.
- Progress is per file, not per byte. Free space on the target is not checked beforehand (the folder app has no reliable way to say); sizes are shown in the dialog, and a full target fails the copy with a message.
- A share cannot be verified or continued: MotoCam cannot know what the receiving app did. After Share, keep the ride (do not delete or unlock it) until the receiving app has finished reading the files. In messengers, send the files as documents, not as video, or the video is re-encoded.
- A ride still in an old storage folder (not yet moved to private storage) can be exported to a folder but not shared.
- `manifest.json` carries no app version, and neither it nor the README is signed.
- The key that signs rides is made by the phone and certified by no one, and every export from one install carries the same public key, so exports with ride data can be linked to each other. The signature does not prove the footage is genuine.
- If the ride file changes while it is copied, the export stops with a message, and the folder keeps that copy of the ride data without a manifest or README until the export is run again.
- A skipped file reports `synced: true` although this run did not sync it (it was written by an earlier run).
- A failure in the export flow other than the export's own failures (for example a crash while planning) shows no message; the migration hold is still released.
- On some folder apps a refused document create surfaces as "could not write" (`WRITE_FAILED`) rather than "this folder cannot be written".
- Section export: the start of a trimmed clip snaps back to the video keyframe at or before the chosen second, so a section starts up to a moment early (usually under 1 s; on the 13 Nov ride the keyframes were 0.6 to 0.8 s apart with occasional gaps of 2 to 4 s). The end is exact. The README and the manifest give the real range of every file.
- Section export: trimmed files are cut copies made without re-encoding, not the original recordings. They keep the original clip names, their bytes and SHA-256 differ from the original clips' and from the hashes recorded in the ride data, and a section has no ride data, signature or integrity claim, so it cannot be checked against the ride's checksums. The README says so.
- Section export: the clock times in the dialog and the README come from the ride's start time (`createdAt`), which for a ride without `startedAt` is the file's modification time and can then be wrong (the manifest's `fromMs`, `toMs` and `actualFromMs` are offsets and are not affected). The lock and incident marks under the slider assume the slider's default 24 px edge inset and are not checked on a phone.
- Section export: if a clip cannot be cut (`TRIM_FAILED`) the export fails with `Could not cut <file> for this section. Pick another section, or export whole clips.`
- Not covered by automated tests: the export flow in the two screens end to end (only the dialog and the gate are tested), and a ride file that changes between its first read and its re-hash (`SOURCE_CHANGED`). The Kotlin side has no unit tests; it is only compiled.
- Diagnostic log: `Diagnostics.kt` (the native crash handler, the session info and the exit reasons) has not been compiled or run on a phone yet; the Dart side is unit tested. A crash in native (C or C++) code is seen only at the next start, through the exit reasons (Android 11 and later), without its tombstone. Dart lines still in the buffer when the process is killed are lost (errors are written at once, info lines within 2 s).
- Not checked yet: see the TODO sections below.
