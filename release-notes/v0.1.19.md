## MotoCam v0.1.19

Release date: 2026-11-20 (tag `v0.1.19`). Pre-release with a debug APK, like v0.1.18. `pubspec.yaml` is at `0.1.19+19` (Android versionName 0.1.19, versionCode 19).

### Upgrade notes / breaking changes

- The APK is debug-signed with the same key as v0.1.17 and v0.1.18 and has a higher versionCode, so it installs over v0.1.18 without uninstalling; rides and settings are kept. If Android refuses it over another MotoCam build, do not uninstall without saving your rides first: uninstalling deletes the rides in MotoCam's private storage.
- The ride JSON format is unchanged, and no existing file is rewritten. New files appear only in the export folders the rider picks (`MotoCam ride <id> (<choice>)`, holding the clips, the ride JSON, `manifest.json` and `MOTOCAM-EXPORT.txt`), in a staging folder in the app's cache directory (`ride_export/`, for Share and while an export runs) and in `<filesDir>/diagnostics` (the diagnostic log).
- The Android manifest gains a FileProvider (not exported, read grants only) that the Share action uses; it adds no permission.
- Installing over v0.1.13 or earlier: read the upgrade notes of v0.1.14 first (rides move to private storage and are no longer reachable over USB).

### Highlights

- **Ride export to a folder and the share sheet (roadmap T0-1).** The ride's actions menu in Ride History, and a new menu in the playback app bar, now offer **Export to folder** and **Share** (Android).
  - One dialog chooses the clips (locked and incident clips, all clips, or a section of the ride, with counts and sizes) and, for whole clips, whether to include the ride data (route, speed every second and private file paths; needed to check the signature). Leaving the ride data out hands over video only, with no key material in the export.
  - **Export to folder** copies into a folder the rider picks, in a subfolder named for the ride and the choice, so running the same choice again continues it. Every copy is read back and hashed; a file already there and equal is skipped; a different file of the same name (same size with other content, or longer) is never overwritten; a shorter one is a partial copy from a killed run and is replaced. The clips come first, then the ride JSON (byte for byte, so its checksum and signature stay valid), then `manifest.json` and `MOTOCAM-EXPORT.txt`. A folder without `MOTOCAM-EXPORT.txt` is an incomplete export.
  - **Share** opens the Android share sheet with the same files through a read-only FileProvider.
  - Each clip is also compared with the hash recorded when the ride was saved. A clip that differs, or has none, is still exported and is labelled in the manifest and the README.
  - `MOTOCAM-EXPORT.txt` says in plain words what the export is, what its integrity line means (signed, unsigned checksums, older format, failed or no integrity data), which clips are not included and why, how to check the clip hashes, the payload hash (with a Python 3 recipe and its number caveat) and the signature (with an `openssl` recipe for a POSIX shell, which prints `Verified OK`), and what to keep private. `manifest.json` (format 1) holds the same facts for programs. Neither file is signed. The format is documented in `docs/data-formats.md`.
  - One export runs at a time. It is refused while a recording starts, runs or stops, while the migration, import or storage budget runs, and while the ride file is being saved. A recording that starts pauses it; it can be run again to continue. A ring on the ride (or a spinner in playback) shows progress and stops the export when tapped. The screen stays on while it runs.
- **Exact per-second sections.** The third clips choice, **A section of the ride** (any ride with a timeline, one-clip rides included), exports exact seconds, video only. A two-handle slider in whole seconds over the ride, with clip-start ticks and lock and incident marks, and `-1 s` and `+1 s` buttons for each end, shows a live label such as `05:12 to 06:40 (1 min 28 s), 2 files, about 310 MB`. It starts on the first minute from Ride History, and from playback on 30 s before to 30 s after the playhead. Clips inside the range are copied unchanged; a clip cut by either end is trimmed without re-encoding and keeps its original file name. A section carries no ride data and no signature, and the dialog says so. The folder is named `MotoCam ride <id> (section 05m12s to 06m40s)`, the manifest says `clips: "section"` with a `section` object (`fromMs`, `toMs`, `actualFromMs`) and, per file, `trimmed`, `clipFromMs` and `clipToMs` (for a trimmed clip, the last sample actually written), and the README gives the section in ride time and clock time and, per file, `(trimmed)` or `(whole clip)` with its range inside the clip. Running the same section again replaces the trimmed copies.
- **Persistent diagnostic log, with Share and Clear in Settings.** App errors are now kept on the phone in a diagnostic log (`<filesDir>/diagnostics/app.log`, rotated at about 1 MB, two files kept), so a tester can send what went wrong: errors the app caught, framework and uncaught errors with their stack traces, uncaught Android exceptions (written before the app closes), a header at each start (app version, build, phone model, Android version) and, on Android 11 and later, why the app's process ended before (crash, native crash, freeze (ANR) with part of its trace, low memory and so on). It never holds a position, speed or route, web addresses are cut to their host, and the piece of file text a parse error quotes is removed. The recording settings sheet's About area has **Share diagnostic log** (with a confirm saying what the log holds and that it has no location) and **Clear diagnostic log**. Console output is unchanged.
- **Fix: red error screens in Recording Settings.** The settings sheet keyed its dropdowns by their bare values, so two settings holding the same number gave two dropdowns the same key: for example the High Detail preset (24 fps) beside the default loop buffer of 24 segments, 60 fps beside 60 s segments, or a 300 ms speed refresh beside 300 s segments (bitrate against the loop buffer and the storage budget could collide the same way). Flutter then reported duplicate keys and the sheet turned into a red error screen, and closing it could show another. **v0.1.13 to v0.1.18 have this bug (the published pre-releases v0.1.14 to v0.1.18 included): users of any of them who change recording settings can hit it.** Each dropdown key now carries its field's name; regression tests reproduce the error screens without the fix.
- **Documentation.** `docs/data-formats.md` (the export folder, the manifest, the README and the checking steps), `docs/platform-integration.md` (the `ride_export` and diagnostics channels, request code 7103, the FileProvider and `Diagnostics.kt`), `docs/architecture.md`, `docs/features.md`, `docs/playback-and-history.md` and `docs/development.md` describe ride export and the diagnostic log.

### Known limits

- **Share to Files by Google delivers only the clip and `MOTOCAM-EXPORT.txt`, not the two .json files** (seen once, cause open: MotoCam or the receiving app). When the ride data or the manifest matter, use Export to folder, or check that the receiving side has every file.
- **On a OnePlus 9 the video is about 10 Mbps when 8 Mbps is asked for** (about 25% larger files), seen on one ride on another branch's build whose bitrate path (app and camera plugin) is the same as this release's; the vivo phone records near the requested rate. The ride file's `appliedBitrateMbps` repeats the request, so it says 8. The storage estimates assume at least 20 Mbps and are not affected.
- Once, right after installing a build (`d70a353`), the first START tap did nothing and logged nothing; a second tap started. It did not happen after the next install and is not explained.
- No resume journal and no saved folder grant: to continue a stopped export, run it again and pick the same folder; files already there are skipped, and each skip reads both copies again to hash them.
- Progress is per file, not per byte. Free space on the target is not checked beforehand (the folder app has no reliable way to say); sizes are shown in the dialog, and a full target fails the copy with a message.
- A share cannot be verified or continued: MotoCam cannot know what the receiving app did. After Share, keep the ride (do not delete or unlock it) until the receiving app has finished reading the files. In messengers, send the files as documents, not as video, or the video is re-encoded.
- A ride still in an old storage folder (not yet moved to private storage) can be exported to a folder but not shared.
- `manifest.json` carries no app version, and neither it nor the README is signed.
- The key that signs rides is made by the phone and certified by no one, and every export from one install carries the same public key, so exports with ride data can be linked to each other. The signature does not prove the footage is genuine.
- If the ride file changes while it is copied, the export stops with a message, and the folder keeps that copy of the ride data without a manifest or README until the export is run again.
- A skipped file reports `synced: true` although this run did not sync it (it was written by an earlier run). A re-run into an existing folder rewrites `manifest.json` and `MOTOCAM-EXPORT.txt` (new `exportedAt`) even when every clip is skipped.
- A failure in the export flow other than the export's own failures (for example a crash while planning) shows no message; the migration hold is still released.
- On some folder apps a refused document create surfaces as "could not write" (`WRITE_FAILED`) rather than "this folder cannot be written".
- Section export: the start of a trimmed clip snaps back to the video keyframe at or before the chosen second, so a section starts up to a moment early (usually under 1 s; on the 13 Nov ride the keyframes were 0.6 to 0.8 s apart with occasional gaps of 2 to 4 s). The end is exact. The README and the manifest give the real range of every file.
- Section export: trimmed files are cut copies made without re-encoding, not the original recordings. They keep the original clip names, their bytes and SHA-256 differ from the original clips' and from the hashes recorded in the ride data, and a section has no ride data, signature or integrity claim, so it cannot be checked against the ride's checksums. The README says so.
- Section export: the clock times in the dialog and the README come from the ride's start time (`createdAt`), which for a ride without `startedAt` is the file's modification time and can then be wrong (the manifest's `fromMs`, `toMs` and `actualFromMs` are offsets and are not affected). The lock and incident marks under the slider assume the slider's default 24 px edge inset and are not checked on a phone.
- Section export: if a clip cannot be cut (`TRIM_FAILED`) the export fails with `Could not cut <file> for this section. Pick another section, or export whole clips.`
- Not covered by automated tests: the export flow in the two screens end to end (only the dialog and the gate are tested), and a ride file that changes between its first read and its re-hash (`SOURCE_CHANGED`). The Kotlin side has no unit tests; it is only compiled.
- Diagnostic log: it has not run on a phone. `Diagnostics.kt` (the native crash handler, the session info and the exit reasons) compiles in a debug build; the Dart side is unit tested. A crash in native (C or C++) code is seen only at the next start, through the exit reasons (Android 11 and later), without its tombstone. Dart lines still in the buffer when the process is killed are lost (errors are written at once, info lines within 2 s). A line seen twice among the last 16 distinct lines is then only counted for the rest of the session (while it stays among them); the count is written by the next flush that another line, a pause or a share causes, so a kill before that loses it.
- Not checked on a phone: see "Checked on a phone" above; also the storage budget, Android 9 and 10, Android 14 or later on this release's code, and a release-signed build.
- The known issues of v0.1.18 still apply (2160p 60 fps clips hold about 42 to 45 frames a second; a locked-phone roll was rechecked only at 1080p 30 fps). Crash detection (jolt + confirm) has now run on one real ride, on the other branch's build above, with no false lock.
